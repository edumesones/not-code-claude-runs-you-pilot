## Phase Assignments

### Phase 1: INTERVIEW
**Agents:** None (human-driven with `spec-architect` skill)

### Phase 2: THINK CRITICALLY
**Agents:**
- **A6 (architect)** — Runs adversarial review (Step 9 of 11-step protocol)
- **Trigger:** After human completes Steps 1-8
- **Execution:** `Task` sub-agent
- **Input:** `analysis.md` (Steps 1-8 completed)
- **Output:** Step 9 adversarial findings appended to `analysis.md`

### Phase 3: PLAN
**Agents:**
- **A6 (architect)** — Validates design against analysis findings
- **Trigger:** After `implementation-planner` produces `design.md` + `tasks.md`
- **Execution:** `Task` sub-agent
- **Input:** `design.md`, `tasks.md`, `analysis.md`
- **Output:** Validation report, issues flagged in `design.md`

### Phase 4: BRANCH
**Agents:** None (automated by `git-automator`)

### Phase 5: IMPLEMENT
**Agents & Orchestration:**

```
┌─────────────────────────────────────────────────────────────┐
│ PARALLEL (worktrees via fork-feature):                       │
│   A1 (implementor) — executes tasks from tasks.md           │
│   A5 (test-writer) — writes tests alongside implementation  │
│                                                              │
│ SEQUENTIAL RELAY (every 3 tasks / checkpoint):               │
│   A2 (reviewer)     → reviews A1's code                     │
│   A3 (bug-detector) → scans for bugs in reviewed code       │
│                                                              │
│ OPTIONAL:                                                    │
│   A4 (doc-writer)   → documents completed components        │
└─────────────────────────────────────────────────────────────┘
```

**Checkpoint Protocol:**
1. A1 completes 3 tasks → commits + pushes
2. A2 reviews changes since last checkpoint → produces review feedback
3. A3 scans for bugs → produces bug report
4. A1 addresses feedback → continues to next 3 tasks
5. Repeat until all tasks complete

### Phase 5.5: VERIFY
**Agents:**
- **A3 (bug-detector)** — Analyzes test results, identifies root causes
- **A5 (test-writer)** — Fixes failing tests
- **Execution:** Sequential relay (A3 analyzes → A5 fixes)

### Phase 6: PR
**Agents:**
- **A2 (reviewer)** — Final comprehensive review
- **A4 (doc-writer)** — Generates PR description with test results
- **Execution:** Sequential relay (A2 review → A4 PR description)

### Phase 7: MERGE
**Agents:** None (human approval required)

### Phase 8: WRAP-UP
**Agents:**
- **A4 (doc-writer)** — Generates `wrap_up.md` with learnings
- **A6 (architect)** — Captures architectural learnings and pattern changes
- **Execution:** Sequential relay

## Agent Derivation Rules

> Used by `agent-designer` skill to determine which agents a project needs.

| Project Characteristic | Detected By | Agents Added/Modified |
|----------------------|-------------|----------------------|
| Has backend code | Stack includes backend framework | A1 splits: `implementor-backend` |
| Has frontend code | Stack includes frontend framework | A1 splits: `implementor-frontend` |
| Has API endpoints | Backend with REST/GraphQL | A2 gains API review focus |
| Has database | Stack includes DB | A3 gains data integrity focus |
| Has authentication | Features mention auth/login | A3 gains security audit focus |
| Has external APIs | Features mention integrations | A3 gains contract testing focus |
| Has browser UI | Frontend with HTML/CSS | A5 gains E2E browser test focus |
| Is security-sensitive | Finance, health, auth-heavy | A3 promoted to dedicated security agent |
| Has ML/data pipeline | Stack includes ML tools | A1 gains `implementor-data` variant |
| Is documentation-heavy | API product, SDK, library | A4 becomes required (not optional) |

### Splitting Rules

When A1 (implementor) splits by domain:
- Each split gets its own worktree
- Each split only works on files in its domain
- Splits execute in PARALLEL

When A3 (bug-detector) gains multiple focuses:
- Focuses execute SEQUENTIALLY (each pass finds different issues)
- Each focus has its own checklist in RULES.md

## Execution Model Reference

| Model | When to Use | Mechanism |
|-------|-------------|-----------|
| **Task sub-agent** | Within-phase agents (reviewer, bug-detector) | Claude `Task` tool with RULES.md prompt |
| **Worktree** | Parallel implementation (backend + frontend) | `fork-feature` skill |
| **Sequential** | Simple 2-agent relay | Same session, sequential prompts |

### Task Sub-Agent Template

```
Task prompt = [
  "You are agent {id} ({name}).",
  "Your RULES: {content of RULES.md}",
  "Phase context: {phase-specific files}",
  "Your input: {previous agent's output or phase trigger}",
  "Produce: {expected output format}",
  "Self-verify using: {harness checklist}"
]
```

---

## Fallback: Single-Agent Mode

If `docs/agents.md` does not exist in a project, the system operates in legacy single-agent mode:
- All phases run exactly as before
- No orchestrator, no relay, no sub-agents
- Fully backward compatible
